# 一、为什么要做这件事

我们每两周要对 Top 应用做一次 NSS（问卷满意度） 分析。但 NSS 本身有几个天然短板，仅靠它很难真正回答“为什么”和“接下来做什么”：

- 只有分数、没有原因。打分的人大多是“沉默的大多数”，很少说清自己到底哪里不满意。

- 反馈滞后。新版本上线后，NSS 的变化往往要等很久才显现，无法及时判断“刚更新的功能是不是用户当下要的”。

- 缺少归因能力。NSS 只告诉你“分降了”，不告诉你“为什么降”“是哪个功能缺失导致的”。

而 应用市场评论 恰好补上了这些缺口——它是用户最原始的声音，实时、公开、可批量获取，包含评分、机型、地域、时间，能直接和版本迭代节点对齐做归因。

我们要做的，是把“读评论→出结论”这件事，从“靠个人手感的一次性劳动”，变成一条标准化、可复用、同事也能上手的流水线。这就是本次“能力固化”的目标。

# 二、整体流程与方法论

我们把整个分析拆成三步，并把每一步固化成一个独立的 Skill（能力模块）。三步前后衔接，但也能各自独立使用：

图1：应用评论满意度分析三步流水线

| 步骤 | Skill 名称 | 职责 | 可独立入口 |
| --- | --- | --- | --- |
| ① 采集与标签化 | app-review-tagging | 原始评论 → 结构化标签数据集 | 有截图/表格时 |
| ② 多维分析 | app-satisfaction-analysis | 标签数据 → 6类分析 + 6类图表 | 已有标签数据时 |
| ③ 报告撰写 | app-satisfaction-report | 结论+图表 → 七段式 Word 报告 | 只需出报告时 |

核心方法论：用户的差评，本质是“需求未被响应”的信号，而不是对产品的否定。所以分析不止看“分多低”，更要回答“为什么变”“用户最想要什么”“哪类人/设备最不满”，并尽量用版本上线节点做因果归因——这是整套分析最有价值的地方。

# 三、Skill ① 评论采集与标签化（app-review-tagging）

本 Skill 负责流程的第一步：把零散的原始评论，转成带统一标签的结构化数据集——所有后续分析的地基。此处做简要介绍，详细标签判定细则已固化在 Skill 内置的 tagging_schema.md 中。

## 3.1 输入规格

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 日期 | 日期 | 是 | 评论发布日期，格式 YYYY/MM/DD 或 YYYY-MM-DD |
| 省份 | 字符串 | 是 | 用于地域维度分析 |
| 机型 | 字符串 | 是 | 原始机型串，如 HUAWEIPura80Pro+ |
| 评分 | 整数 1-5 | 是 | 对应 非常差/不太好/还可以/很不错/非常棒 |
| 评分文字 | 字符串 | 否 | 平台文案，可用于校验评分 |
| 评论内容 | 字符串 | 是 | 用户原文，标签化的核心输入 |
| 用户名 | 字符串 | 否 | 脱敏后可保留，用于去重 |

## 3.2 标签化字段（9 类）

| 标签字段 | 类型 | 取值范围 |
| --- | --- | --- |
| is_valid | 布尔 | true / false |
| 功能模块 | 数组 | 核心播放｜内容发现｜社交互动｜鸿蒙特性｜账号体系｜个性化｜体验问题｜其他 |
| 问题类型 | 单选 | BUG｜功能缺失｜体验差｜性能问题｜广告问题｜鸿蒙适配好评｜正面反馈｜功能建议｜吐槽抱怨 |
| 紧急度 | 单选 | 高 / 中 / 低 |
| 情感强度 | 整数 | -2 到 +2 |
| 表达形式 | 单选 | 理性评价｜情绪宣泄｜对比抱怨｜求助提问｜功能许愿｜调侃玩梗 |
| 涉及竞品 | 字符串/null | 竞品名 或 null |
| 核心诉求 | 字符串 | 一句话反推用户真正想要什么 |
| PM行动建议 | 字符串 | 一句话可执行建议 |

## 3.3 两种执行方式

- 方式一 · 直接对话处理：评论量 ≤200 条时，直接在对话中逐条阅读、判断并输出标签。质量最高，适合需要细腻判断的小批量。

- 方式二 · API 批量标签化：评论量大时，调用低成本模型（火山引擎 / DeepSeek 等）批量打标。Skill 内附批处理脚本模板 batch_tag.py，填入 API 配置即可运行。无论哪种方式，都应抽查 5%-10% 人工校验。

## 3.4 输出规格

| 文件 | 格式 | 说明 |
| --- | --- | --- |
| *_tagged.jsonl | JSON Lines | 每行一条带全部标签的 JSON，信息最全 |
| *_tagged.csv | CSV (UTF-8 BOM) | 数组字段拼接为逗号分隔字符串，方便 Excel 透视 |
| 统计摘要 | 文本/表格 | 有效评论数、去重/无效数、周期范围、平均评分 |

跨平台注意：CSV 输出务必带 UTF-8 BOM 头（\xEF\xBB\xBF），否则 Excel 打开中文乱码。JSONL 则保持纯 UTF-8。

# 四、Skill ② 满意度多维分析（app-satisfaction-analysis）

本 Skill 是整条流水线的“分析引擎”，负责从标签化数据中提取可支撑决策的结论，并产出一套标准图表。下面逐一拆解六类分析的目的、数据准备、计算方法、图表规格、解读要点和注意事项。

## 4.0 输入输出总规格

### 输入

| 项目 | 规格 | 说明 |
| --- | --- | --- |
| 标签数据 | CSV/JSONL | 来自 Skill ① 的 *_tagged 文件，必含：日期、省份、机型（含设备系列列）、评分、功能模块、问题类型、核心诉求 |
| 版本更新记录 | 文本/截图 | 官方版本历史，用于在趋势图上标注事件节点、做归因 |
| 分析周期 | 日期区间 | 如 2026/05/04-06/13，决定聚合范围 |

### 输出

| 输出物 | 格式 | 用途 |
| --- | --- | --- |
| 图表文件（6类） | PNG, ≥150dpi | 直接嵌入报告，命名 图N_主题.png |
| 分析结论清单 | Markdown/文本 | 每类分析一段结论 + 管理启示 |
| 汇总指标表 | CSV/表格 | 总体均分、分布、周度趋势、Top10 诉求、设备梯度 |
| 原始聚合数据 | CSV | 周度聚合、主题聚合、设备聚合等中间表，供复查 |

所有图表必须遵循统一配色（满意度语义色：红 <2.2 / 橙 2.2-2.6 / 蓝 2.6-3.0 / 绿 ≥3.0），中文标题，关键数值标注在图元上。详见 Skill 内置 chart_specs.md。

## 4.1 分析一：大盘评分分布

### 目的

定基线——回答“当前整体处于什么状态”。这是所有人最先看的数字，也是后续所有对比的锚点。

### 数据准备

- 统计有效评论总数（is_valid=true）。

- 按评分（1-5星）分组计数，算各星级条数与占比。

- 计算平均评分（加权均值）。

- 计算差评率 = (1星+2星) / 总数；好评率 = (4星+5星) / 总数。

### 计算方法

| 指标 | 公式 | 示例 |
| --- | --- | --- |
| 平均评分 | Σ(评分×条数) / 总条数 | 2.49 |
| 差评率 | (1星+2星) / 总条数 | 53% |
| 好评率 | (4星+5星) / 总条数 | 25% |
| 中评占比 | 1 - 差评率 - 好评率 | 21% |

### 图表规格：评分分布柱状图

- 5 个柱，横轴标签用平台文案 + 星级，如“非常棒(5星)”。

- 柱顶标注条数 + 占比%（如“222 / 36%”）。

- 配色：5星用绿、4星用浅绿、3星用黄、2星用橙、1星用红，两极对比鲜明。

- 标题格式：“图5 评分分布(N=622) — 呈两极分化”（根据实际分布特征调整后缀）。

### 解读要点

- 判断分布形态：U 型两极分化、正态集中、还是偏左长尾？形态决定解读口径。

- 定性低分性质：“迁移期功能落差”（可治理、可预期）vs“质量危机”（需紧急修复）——结论不同，对策完全不同。

- 结尾给管理启示：如“当前低分并非质量危机，而是迁移期功能落差的集中释放，会随功能补齐快速回正”。

### 注意事项

- 去掉 is_valid=false 的评论后再算，否则无效评论（如纯表情）会拉偏均分。

- 如果“未识别评分”的条目较多（>5%），应单独说明并在附录标注。

## 4.2 分析二：走势分析与归因

### 目的

回答“满意度在变好还是变坏”“为什么变”——这是全套分析的因果核心，价值最高的部分。

### 数据准备

- 按自然周聚合（周一起始或自定义），每周算：评论量、平均评分、差评率、好评率。

- 同步准备版本更新记录，标注每个版本的上线日期和主要功能。

- 如果分析周期跨月，需注意周的切分是否一致，建议全程用同一种切分逻辑。

### 计算方法：三步走

第一步：周度指标表

| 周次(起始) | 评论量 | 平均评分 | 差评率 | 好评率 |
| --- | --- | --- | --- | --- |
| 05/04 | 85 | 2.45 | 52% | 21% |
| 05/11 | 74 | 2.53 | 51% | 23% |
| 06/01 | 160 | 2.82 | 46% | 37% |

（以上为示例数据）

第二步：版本上线前后对比

把时间轴按“关键版本上线”切成前后两段，对比均分、差评率、好评率、样本量的变化（如 +0.22分、+8pp好评率）。这是量化归因的直接证据。

第三步：“呼声→上线”功能反转分析（最硬证据）

把“曾被反复呼吁、随后真的上线了”的功能切片出来，对比上线前后该功能相关评论的平均评分。例如 bubble 上线前均分 2.30 → 上线后 3.77，这证明“补齐一个高呼声功能 = 直接兑换满意度”。

### 图表规格

图1 · 周度趋势组合图

- 柱状图 = 评论量（浅蓝，左轴）。

- 实线折线 = 平均评分（深蓝，数据点标注数值）。

- 虚线折线 = 差评率（红色，右轴比例）。

- 版本上线节点用竖虚线 + 文字标注（如“6/1-6/3 bubble/DM/扑淘上线”），这个标注是因果归因的核心视觉锚点。

图3 · 呼声→上线反转分组柱状图

- 每个功能两根柱：灰色 = 上线前均分，绿色 = 上线后均分，柱顶标数值。

- 加一条红色水平虚线 = 全体均分参考线。

- 如果上线后某功能均分反而没涨，要分析原因（如 Weverse DM 只涨了 0.29 因为有白屏 bug）。

### 解读要点

- 找转折点：均分突然拉升/下降的那一周，对齐到版本事件，不要只描述“涨了”，要说“为什么涨”。

- 评分回落不等于质量倒退：新功能上线后用户期待被抬高、注意力转向下一个未满足需求，这是正常的“期望升级效应”。

- 不护短：如果回落是因为广告投诉发酵，就如实说，这种坦诚是报告可信度的来源。

### 注意事项

- 周度切分要全程一致（都用自然周或都用版本发布日切），否则跨期对比会失真。

- 样本量太小的周（<20条）应标注“样本量不足、仅供参考”，避免因 2-3 条极端评论导致均分跳变被过度解读。

- “呼声→上线”分析要区分“功能上线前的催更评论”和“功能上线后的使用反馈”，按上线日期切片，不要混在一起。

## 4.3 分析三：重要功能诉求

### 目的

回答“用户最关心什么”“最想要什么”——直接指导产品排期。

### 数据准备

- 以“核心诉求”标签为主维度，辅以“功能模块”“问题类型”做交叉。

- 需要做两层归并：先把近义诉求归并为“主题桶”（如“一起听/好友互动”），再在桶内统计“单一需求点名数”。

- 原因：宽口径“主题桶”用于衡量话题热度；窄口径“单一需求”用于排优先级。两者数字会不同，都需要，但不能混用。

### 计算方法

- 按主题桶统计提及数（一条评论可命中多主题），降序排列取 Top 10。

- 每个主题额外算：均分、差评率。

- 优先级排序公式：综合“提及声量 × 差评强度 × 与安卓/竞品的落差”三因子，而非单纯看提及数。

### 图表规格

图2 · 主题热度+满意度横向条形图

- 横向条形按提及数降序排列。

- 条的颜色 = 该主题均分对应的满意度语义色（红/橙/蓝/绿），一张图同时表达“声量大小”和“情绪好坏”。

- 条尾标注“N条·均分·差评率%”。

- 标题含图例说明：“红=差评重灾区<2.2 橙=2.2-2.6 蓝=2.6-3.0 绿=口碑正向≥3.0”。

（可选）Top 需求周度变化趋势

取 Top 5 需求，画折线图（X=周次，Y=该周提及数），观察哪个需求在升温、哪个在降温。适用于需求在报告周期内有显著波动的场景。

### 解读要点

- 区分“已上线·回正”和“仍缺失”：已上线功能（如 bubble）的颜色应该变绿、差评率下降，这本身是正面证据。

- 识别“满意度毒药”：有些主题提及数不是最高，但均分极低（如广告 1.62），对品牌信任的伤害远超其排名暗示的程度。

### 注意事项

- 主题归并的口径要固化在 Skill 中（关键词表），每期新增的主题词需追加并记录，否则跨期不可比。

- 一条评论命中多主题时，每个主题都 +1 计数，但总条数仍按独立评论算，两者不应混淆。

- 用户原话“画像”（代表性引用）对汇报很有说服力，每个 Top 主题至少摘 1-2 条典型原话。

## 4.4 分析四：设备维度分析

### 目的

回答“哪类设备的用户最满意/最不满”“不同设备用户的痛点有什么差异”。

### 数据准备

- 用 Skill ① 的机型归一化结果，将评论按设备系列分组。

- 标准设备系列（可按需扩展）：

| 设备系列 | 匹配关键字 | 用户画像特征 |
| --- | --- | --- |
| nova系列 | nova | 年轻用户，中高端，满意度居中偏高 |
| Pura系列 | pura, p60, p70 | 旗舰用户，深度付费、重度社交，最挑剔 |
| Mate直板机 | mate（非matex/matepad） | 旗舰商务，重度付费，差评主力之一 |
| MateX折叠屏 | matex, pocket | 折叠形态，关注横屏/分屏体验 |
| 平板系列 | matepad, pad | 听歌为主，社交依赖低，满意度偏高 |
| 畅享系列 | 畅享, enjoy | 中低端，关注性能/广告体验 |

注意匹配顺序：先判 matepad → matex → pura → nova → 畅享 → mate → 其他，否则 Mate 直板会误吞折叠屏与平板。

### 计算方法

- 每个设备系列算：平均评分、样本量（n）、差评率。

- 按均分降序排列。

- （进阶）每个设备系列内再按周聚合画走势折线，观察不同设备对版本迭代的响应差异。

### 图表规格：设备满意度横向条形图

- 横向条形，按均分降序。

- 条色 = 均分对应语义色（红/橙/蓝/绿）。

- 条尾标注“均分 (n=样本量)”。

- 加一条灰色竖虚线 = 整体均分参考线。

### 解读要点

- 不只看“谁高谁低”，更要挖每类设备的专属短板：如平板“没有横屏播放器”、畅享“广告多+卡顿”、Pura“社交功能缺失感最强”。

- 样本量差异大时（如畅享只有 12 条），要标注“样本量较少，结论仅供参考”。

### 注意事项

- 新机型上市时需及时更新机型映射表（device_mapping.md），否则新机型会被归入“其他/未知”。

- 折叠屏和平板用户虽然样本少，但痛点独特（横屏、分屏），不能因为样本少就忽略。

## 4.5 分析五：设备 × 舆情需求热力图

### 目的

交叉分析“哪类设备最缺哪类功能”——一张图同时呈现设备和功能两个维度，是定向优化的指南针。

### 数据准备

- 行（Y轴）= 功能/诉求项（取 Top 8-10，太多则图过于密集）。

- 列（X轴）= 设备系列。

- 单元格值 = 该设备群体对该功能的“需求强度”。

### 计算方法：需求强度的三种口径（择一使用，在报告注明）

| 口径 | 计算方式 | 适用场景 |
| --- | --- | --- |
| 提及数 | 该设备×该功能的评论条数 | 最直观，但受样本量影响大 |
| 提及占比 | 提及数 / 该设备总评论数 × 100% | 消除样本量差异，推荐使用 |
| 加权差评强度 | 提及数 × (1-该主题均分/5) | 同时考虑声量和不满程度 |

### 图表规格：热力图

- 颜色用顺序色系（浅→深），如 浅橙→深红，深色 = 需求强。

- 每个单元格内标数值。

- 标题说明口径：如“色深=提及占比高”。

### 解读要点

- 找“深色集中区”——即某类设备对某类功能需求特别强烈的交叉点，这是定向优化的优先级。

- 对比行方向：看某功能是“所有设备都缺”（全行深色）还是“特定设备特别缺”（局部深色）。

### 注意事项

- 样本量极少的设备系列（如畅享 12 条），占比波动大，热力图颜色容易被极端值带跑，建议标注 n 值或设样本量阈值。

- 功能项数控制在 8-10 个以内，太多会让热力图难以阅读；可以把“其他”合并。

## 4.6 分析六：人群画像分析

### 目的

把抽象的数据还原为具体的“人”——让产品团队能说“这个版本是给XX人群做的”，而不是“给均分2.4的人做的”。

### 数据准备

- 综合每条评论的以下标签：表达形式、涉及竞品、核心诉求、功能模块、设备系列、情感强度。

- 按行为特征聚类（不需要算法，人工归纳即可），提炼出 4-6 类有代表性的人群。

### 画像模板（每类人群输出以下维度）

| 维度 | 示例 |
| --- | --- |
| 人群名称 | “追星粉丝” |
| 关联身份/职业 | 学生、年轻女性为主 |
| 典型设备 | nova 系列、Pura 系列 |
| 核心诉求 | bubble、由你榜、勋章、打投 |
| 情绪基调 | 焦虑、催更、上线后感恩 |
| 代表性原话 | “被家族 T 了”“追星人非常需要由你榜” |
| 产品启示 | 粉丝功能是留存和口碑的杠杆，优先级应高于通用功能 |

### 常见人群类型参考

- 追星粉丝：关注 bubble/由你榜/勋章/扑淘商城，情绪波动大，功能上线后好评转化率最高。

- HiFi 发烧友：关注音质/AudioVivid/耳机适配/QPlay，理性评价为主，是专业口碑传播者。

- 平板轻听党：MatePad 用户，以听歌为主，对社交功能依赖低，但横屏/分屏是专属痛点。

- 从安卓迁移的老用户：最大差评群体，核心情绪是“功能阉割”，对比抱怨为主，但对“适配诚意”有感知。

- 中低端性价比用户：畅享系列，广告敏感、性能敏感，体验底线最容易被击穿。

### 注意事项

- 画像是“定性归纳”而非“精确聚类”，不需要机器学习；但要确保每类画像至少有 10+ 条评论支撑，避免以偏概全。

- 画像要与设备维度交叉验证：如果“追星粉丝”主要集中在 nova/Pura，那 Mate 商务用户可能并不关心 bubble。

- 每类画像至少配 1-2 条用户原话——这是汇报中最有感染力的素材，让数据“说人话”。

# 五、Skill ③ 满意度报告撰写（app-satisfaction-report）

本 Skill 负责流程的最后一步：把 Skill ② 产出的结论和图表，装配成一份结构固定、叙事有因果、可直接交付的 Word 报告。固定结构的价值在于：跨期可比、读者看一次就知道每段在讲什么、新同事照着填就能产出合格报告。

## 5.0 输入输出总规格

### 输入

| 项目 | 格式 | 来源 |
| --- | --- | --- |
| 分析结论清单 | 文本 | Skill ② 输出的六类分析结论 |
| 图表文件 | PNG ≥150dpi | Skill ② 输出的 图1-图6 |
| 汇总指标表 | CSV/表格 | Skill ② 输出的聚合数据 |
| 版本更新记录 | 文本/截图 | 官方版本历史 |
| 分析周期 | 日期区间 | 本期覆盖范围 |

### 输出

| 输出物 | 格式 | 规格 |
| --- | --- | --- |
| 满意度月度报告 | .docx | US Letter / A4，含封面/页眉页脚/表格/内嵌图表 |
| PDF 副本（可选） | .pdf | 用于只读分发，保留排版 |

跨平台兼容：Word 文件以 docx-js（Node.js）或 python-docx 生成均可；表格用 DXA 单位（不用百分比，百分比在 Google Docs 会失真）；字体使用微软雅黑/Arial 等跨平台字体。

## 5.1 报告“主心骨”与写作纪律

写作前先提炼核心命题

每一期报告都应有一个核心命题（如“满意度由功能补齐进度主导，而非质量问题”），所有章节都为这个命题服务。命题从数据中来，不是预设的。

五条写作纪律

- 结论前置：执行摘要直接给判断，不铺垫、不“详见下文”。

- 文字落到“管理启示”：不复述数字（数字交给图表），而是说“这意味着什么”“应该怎么做”。

- 不护短：评分回落要讲真实原因（如期待被抬高、广告发酵），不掩饰；坦诚是可信度的来源。

- 平衡视角：既讲差评，也讲“用户满意、应继续强化的点”，保护团队士气并指明可放大的优势。

- 每段末尾有“所以呢”：如果一段话去掉最后一句还是完整的，说明缺了“管理启示/对策”那一层。

## 5.2 七段式结构逐段详解

以下逐段拆解：每段要回答的问题、必备内容要素、配套图表、好例/差例对照。

### 第一段：执行摘要

| 维度 | 要求 |
| --- | --- |
| 要回答的问题 | 30 秒内让决策者抓住全局判断 |
| 内容要素 | 5 条左右核心判断，每条“加粗主张 + 一句支撑数据”；结尾一句话总结全局因果 |
| 配套图表 | 无图——纯结论，用加粗和颜色承载信息密度 |
| 篇幅 | 半页到一页 |

好例：

“「功能缺失」是满意度第一杀手，而非质量问题。差评多指向‘安卓有、本版没有’的落差，而非崩溃卡顿。”

差例（避免）：

“本月评分有所变化，详见下文。”——没有主张、没有信息、浪费读者时间。

### 第二段：满意度总体表现

| 维度 | 要求 |
| --- | --- |
| 要回答的问题 | 当前处于什么状态？ |
| 内容要素 | 有效评论数、平均评分、评分分布形态判断（U型/正态/偏左）、低分性质定性 |
| 配套图表 | 图5 评分分布柱状图 |
| 结尾必须有 | “管理启示”——如“低分是迁移期落差，可治理、可预期” |

### 第三段：满意度变化趋势与归因分析（因果核心）

| 维度 | 要求 |
| --- | --- |
| 要回答的问题 | 满意度在变好还是变坏？为什么？ |
| 3.1 趋势 | 图1 周度趋势组合图 + 表1 周度指标表；指出转折点并对齐事件 |
| 3.2 归因 | 表2 版本上线前后对比表；量化变化（如均分+0.22） |
| 3.3 关键证据 | 图3 呼声→上线反转图；逐功能展示上线前后均分反转 |
| 关键句式 | “满意度对‘功能上线’高度敏感且响应迅速” |
| 评分回落的处理 | 不说“质量倒退”，给真实归因（期待升级效应 + 广告发酵） |

这是全报告最重要的一段——因为它回答“为什么”，而“为什么”比“是什么”有价值得多。如果只能留一段，留这段。

### 第四段：多维度分析

| 维度 | 要求 |
| --- | --- |
| 4.1 主题维度 | 图2 主题热度+满意度图 + 表3 排行表；区分宽口径“主题桶”和窄口径“需求点名” |
| 4.2 设备维度 | 图4 设备满意度图 + 图6 设备×需求热力图（可选）；给每类设备的专属短板 |
| 4.3 地域维度 | 通常纯文字；若差异不大，直接结论“全国一致、无需地域化运营”，不堆数字不配图 |
| 4.4 人群画像（可选） | 4-6类画像 + 代表原话 + 产品启示 |

### 第五段：用户最迫切的需求（按优先级）

| 维度 | 要求 |
| --- | --- |
| 要回答的问题 | 接下来最应该做什么？ |
| 排序逻辑 | 综合“声量 × 差评强度 × 与安卓/竞品落差”，不是单纯看提及数 |
| 配套图表 | 表4 需求优先级清单：优先级 P0/P1/P2 + 需求 + 声量 + 用户原话画像 |
| P0 解读 | 必须点出：“这是唯一一个声量超过 XX%、横跨所有机型地域的需求” |
| 原话画像的作用 | 让优先级有温度，决策者能“听到”用户的声音 |

### 第六段：用户满意的点（应继续强化）

| 维度 | 要求 |
| --- | --- |
| 要回答的问题 | 我们做对了什么？哪些优势可以放大？ |
| 内容要素 | 从高分评论提炼口碑资产（如快速适配/原生体验/专业音质） |
| 配套图表 | 无图——用高分原话提炼，让正面声音被“听到” |
| 结尾“策略含义” | 把口碑基石写进应用商店介绍、更新文案，做成品牌心智 |

这一段容易被忽略，但对汇报效果至关重要——全篇差评会让团队沮丧，平衡正面视角能保护士气、指明方向。

### 第七段：未来如何持续提升满意度

| 维度 | 要求 |
| --- | --- |
| 7.1 战略原则 | 3条左右：如“以补齐速度为核心KPI”“克制商业化侵蚀”“把适配诚意做成品牌资产” |
| 7.2 分阶段路线图 | 表5：即时(止血) / 本季度(补P0P1) / 中期(对齐安卓) / 长期(建立优势)；每阶段给关键动作+预期满意度区间 |
| 7.3 量化目标 | 下月均分目标（如 2.49→2.80）、核心抓手的预计拉动、体验红线指标 |

### 附录：数据与方法说明

| 维度 | 要求 |
| --- | --- |
| 数据来源 | 渠道、采集方式、去重后有效条数、覆盖周期 |
| 评分映射 | 平台文案→1-5分的对应关系 |
| 主题分类 | 关键词匹配方式、主题数量、多命中规则 |
| 版本对照 | 功能上线时点来源（官方版本历史） |
| 局限性 | ①沉默大多数偏差 ②OCR截断噪声 ③单渠道，建议交叉验证 |

# 六、跨平台迁移指南

三个 Skill 设计上是“应用无关、平台无关”的。从 QQ 音乐迁移到其他 Top 应用（如微信、抖音、小红书），或从华为应用市场迁移到其他评论渠道，只需调整以下配置项，分析框架和报告结构无需改动：

| 迁移场景 | 需要调整的配置 | 所在位置 |
| --- | --- | --- |
| 换一个 App | ① 主题关键词表<br>② 机型映射表（如非华为设备）<br>③ 版本更新记录 | ① Skill② 内置表<br>② Skill① device_mapping.md<br>③ 手动收集 |
| 换评论渠道 | ① 原始字段映射（不同渠道字段名不同）<br>② 评分映射（不同渠道评分尺度不同）<br>③ OCR 脚本（如换平台截图） | ① Skill① 输入规格<br>② Skill① 评分映射<br>③ 外部 OCR 工具 |
| 换分析工具 | 图表生成脚本的运行环境<br>（Python/matplotlib 或换用 Echarts/Tableau） | Skill② scripts/ |
| 换报告工具 | docx-js / python-docx 二选一<br>或换用 PPT / Google Docs 模板 | Skill③ 装配代码 |

## 6.1 文件格式兼容性要点

| 格式 | 注意点 |
| --- | --- |
| CSV | 务必带 UTF-8 BOM 头（Excel 兼容）；数组字段用半角逗号分隔并引号包裹 |
| JSONL | 纯 UTF-8，每行一条 JSON；中文无需转义（ensure_ascii=False） |
| PNG 图表 | ≥150dpi，白底，中文字体嵌入或使用系统可回退的字体 |
| DOCX 报告 | 表格用 DXA 单位（不用百分比）；字体用微软雅黑/Arial；图片用 ImageRun 内嵌 |

## 6.2 Skill 安装与分发

- 每个 Skill 已打包为 .skill 文件（本质是 ZIP 归档），分发给同事后安装即可使用。

- 安装方式：在 Claude 设置中的 Skill 管理页面上传 .skill 文件，或解压到团队共享目录。

- 版本管理：建议在团队 Git 仓库中管理 Skill 源码（SKILL.md + references/ + scripts/），每次迭代留版本号。

# 七、固化的价值与推广计划

## 7.1 三个标准化收益

- 可复用：一次沉淀，长期使用。下一期分析、其他 Top 应用，换数据即可跑同一套流程。

- 可推广：同事拿到 .skill 就能上手，不必口头传授经验；判定口径写进 Skill，避免“各打各的标”。

- 可比较：结构、图表、打标口径统一，跨期、跨人、跨应用的结果才有可比性，趋势才看得准。

## 7.2 同事如何上手（按场景）

| 场景 | 用法 |
| --- | --- |
| 从零做一期完整分析 | 依次用 ①→②→③，从原始截图一路到成品报告 |
| 已有标签数据 | 直接用 ② 出分析与图表，或再接 ③ 出报告 |
| 只需更新本期报告 | 用 ③ 套用七段式结构，填入本期结论即可 |
| 换一个 App / 换平台 | 参照第六章迁移指南，调整配置项即可 |

## 7.3 推广节奏建议

- 本周：把 3 个 .skill 安装到团队公共环境，配本报告 + 已完成的《QQ音乐鸿蒙版满意度报告》作为范例。

- 下两周：挑 1-2 名同事用真实数据各跑一期，收集口径与体验上的问题。

- 一个月内：根据反馈迭代 Skill（主要是标签判定细则与主题词表），固化为团队标准作业流程（SOP）。

- 持续：把“应用市场平均评分”纳入月度 KPI 跟踪，让分析直接服务于满意度提升这一核心目标。

# 结语

这次固化，把“读懂用户原声”这件事，从依赖个人经验，变成了一条人人可跑、结果可比、持续迭代的流水线。它不只是省时间，更是让团队对用户满意度的洞察，能稳定地、可累积地服务于产品决策。

核心要点回顾：

- Skill ① 统一了“怎么打标”——9 类标签、统一口径、两种执行方式。

- Skill ② 固化了“怎么分析”——6 类分析、6 类标准图表、因果归因方法论。

- Skill ③ 规范了“怎么写报告”——七段式结构、写作纪律、好差对照。

- 跨平台迁移只需调配置项——分析框架和报告结构无需改动。

附：随本报告提供 3 个 .skill 文件以及已完成的范例报告，供各位安装试用与参考。
